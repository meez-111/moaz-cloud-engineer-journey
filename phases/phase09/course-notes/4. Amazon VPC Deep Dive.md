## 1. Disaster Recovery (DR) & DR Approaches in AWS

### What is a Disaster?

A **disaster** is any event that causes a significant disruption to business operations – natural disasters (earthquakes, floods), cyberattacks (ransomware, DDoS), human error (accidental deletion), or infrastructure failures (power outage, hardware failure).

### What is Disaster Recovery?

**Disaster Recovery (DR)** is the set of policies, tools, and procedures to enable the recovery or continuation of vital technology infrastructure and systems following a disaster.

**Key principle:** DR must be **ready and tested** – a plan that has never been tested is not a plan.

### Business Impact Analysis

The right DR strategy depends on an analysis to identify the impact of a disaster on the business and finance.

**The output of the disaster analysis:**

| Output | Meaning |
|--------|---------|
| **Cost** | How much will DR cost (infrastructure, personnel, testing)? |
| **RTO (Recovery Time Objective)** | Maximum acceptable downtime. |
| **RPO (Recovery Point Objective)** | Maximum acceptable data loss (in time). |

### DR Approaches in AWS

The four DR strategies range from **low cost / slow recovery** to **high cost / fast recovery**:

| Strategy | Description | RTO | RPO | Cost |
|----------|-------------|-----|-----|------|
| **Backup and Restore** | Back up data to S3; restore when needed. | Hours | Hours | Lowest |
| **Pilot Light** | Keep a minimal version of your infrastructure running (e.g., database replication). | Minutes to hours | Minutes | Low |
| **Warm Standby** | Keep a scaled‑down version of your application running in another Region. | Minutes | Seconds to minutes | Medium |
| **Multi‑Site (Active/Active)** | Run the application in multiple Regions simultaneously. | Seconds | Near‑zero | Highest |

**Cold vs. Hot:**

| Term | Meaning |
|------|---------|
| **Cold** | Infrastructure is not running (Backup & Restore). |
| **Warm** | Partially running (Pilot Light, Warm Standby). |
| **Hot** | Fully running (Multi‑Site Active/Active). |

## 2. NAT – Network Address Translation

### 2.1 What is NAT and Why Do We Need It?

**NAT (Network Address Translation)** allows instances in a **private subnet** to access the internet (for updates, patches, external APIs) while remaining **unreachable from the internet**.

**Why we need it:**
- Private subnet instances have **private IPs only** (no public IP).
- They cannot communicate with the internet directly.
- NAT translates their private IP to a public IP for outbound traffic, and translates the response back.

**Key rule:** NAT must be launched in a **public subnet** (it needs internet access itself). The private subnet's route table must have a default route (`0.0.0.0/0`) pointing to the NAT device.

### 2.2 NAT Instance

A **NAT Instance** is an EC2 instance configured to perform NAT. It is the **legacy** approach.

| Aspect | Description |
|--------|-------------|
| **Launch location** | Must be in a **public subnet**. |
| **Route table** | Private subnet must have a default route pointing to the NAT instance ID. |
| **Source/Destination check** | Must be **disabled** on the NAT instance (it needs to forward traffic not addressed to itself). |
| **Security Group** | Must allow inbound traffic from the private subnet, and outbound to the internet. |
| **Scaling** | Manual – you must resize the instance or build your own HA setup. |
| **Availability** | Single point of failure unless you build custom HA (multiple NAT instances across AZs + scripts to failover). |
| **Bandwidth** | Limited by the instance type. |

**How the NAT instance works:**

```
Private EC2 (10.0.100.10) → NAT Instance (Public Subnet, 54.x.x.x)
                                    │
                                    ▼
                              Internet (translates source IP)
                                    │
                                    ▼
                              Response returns to NAT Instance
                                    │
                                    ▼
                              Forwarded to Private EC2
```

### 2.3 NAT Gateway

**NAT Gateway** is the **AWS‑recommended** managed NAT service.

| Aspect | Description |
|--------|-------------|
| **Management** | Fully managed by AWS – no patching, no scaling, no maintenance. |
| **Availability** | Highly available **within an AZ** (redundant). |
| **Bandwidth** | Can scale up to **45 Gbps per gateway**. |
| **IP address** | Works with **Elastic IP** only (you must allocate an EIP). |
| **Security Groups** | **Cannot** be associated with a Security Group. |
| **Launch location** | Must be in a **public subnet**. |
| **Route table** | Private subnet must have a default route pointing to the NAT Gateway ID. |

**NAT Gateway – AZ‑Independent Architecture for High Availability:**

NAT Gateways are **AZ‑specific**. If the AZ hosting the NAT Gateway fails, the NAT Gateway fails with it.

**Best practice:** Create a NAT Gateway in **each AZ** and configure each private subnet to route to the NAT Gateway in the same AZ.

```
AZ-1a: Public Subnet → NAT Gateway 1a
       Private Subnet → route to NAT GW 1a

AZ-1b: Public Subnet → NAT Gateway 1b
       Private Subnet → route to NAT GW 1b
```

This way, if AZ‑1a fails, the private subnet in AZ‑1b still has internet access via NAT GW 1b.

**Whitelisting with NAT Gateway:**

Because NAT Gateway uses an **Elastic IP**, you can whitelist that IP with third‑party services (e.g., payment gateways, external APIs). This is a common pattern for outbound traffic authorisation.

### 2.4 NAT Instance vs. NAT Gateway

| Feature | NAT Instance | NAT Gateway |
|---------|--------------|-------------|
| **Management** | Self‑managed (you patch, scale, monitor). | Fully managed by AWS. |
| **Availability** | Single instance = single point of failure (unless custom HA). | Highly available within an AZ (redundant). |
| **Bandwidth** | Limited by instance type. | Up to 45 Gbps. |
| **Scaling** | Manual. | Automatic. |
| **Elastic IP** | Can use an EIP. | Must use an EIP. |
| **Security Groups** | Can attach security groups. | Cannot attach security groups. |
| **Cost** | EC2 instance cost + data transfer. | Hourly charge + data processing charge. |
| **Use case** | Legacy, custom requirements, cost‑sensitive small workloads. | **Recommended** for all modern architectures. |

**AWS recommendation:** Use **NAT Gateway** unless you have a specific reason to use a NAT Instance.

## 3. Proxy Server 101

A **proxy server** acts as an intermediary between clients and servers. It forwards client requests to servers and returns responses.

**Forward Proxy:**

```
Client → Proxy Server → Internet (server)
```

| Aspect | Description |
|--------|-------------|
| **Purpose** | Filtering, caching, anonymity, access control. |
| **Filtering** | Allow instances to receive updates from specific URLs only (e.g., OS repositories, AWS services). |
| **Logging** | All outbound traffic is logged on the proxy. |
| **Use cases** | Restricting internet access, caching content, monitoring outbound traffic. |

**Proxy vs. NAT:**

| Feature | NAT | Forward Proxy |
|---------|-----|---------------|
| **Layer** | Layer 3/4 (IP/port translation). | Layer 7 (application level). |
| **Filtering** | No (forwards all traffic). | Yes (can filter by URL, domain, content). |
| **Visibility** | IP‑level only. | Full URL/HTTP visibility. |
| **Use case** | General internet access. | Restricted internet access with filtering. |

## 4. Reverse Proxy

A **reverse proxy** sits in front of web servers and forwards client requests to them. Clients only see the reverse proxy's address, not the backend servers.

```
Client → Reverse Proxy → Backend Servers
```

| Aspect | Description |
|--------|-------------|
| **Purpose** | Load balancing, SSL termination, caching, security. |
| **Load balancing** | Distributes traffic across multiple backend servers. |
| **SSL termination** | Handles HTTPS, passes HTTP to backend (offloads SSL). |
| **Security** | Hides backend server details (no direct client access). |
| **Caching** | Caches static content (like a CDN). |

**Use cases:**
- **ALB/NLB** – AWS Application Load Balancer and Network Load Balancer act as reverse proxies.
- **Nginx / HAProxy** – self‑managed reverse proxy on EC2.
- **CloudFront** – reverse proxy for content delivery.

**Proxy vs. Reverse Proxy:**

| Aspect | Forward Proxy | Reverse Proxy |
|--------|---------------|---------------|
| **Position** | In front of the client. | In front of the server. |
| **Client knowledge** | Client knows it's using a proxy. | Client does not know the proxy exists. |
| **Use case** | Filtering, anonymity, caching for clients. | Load balancing, SSL termination, security for servers. |

## 5. Bastion Host

A **Bastion Host** (also called a Jump Box) is a server that provides secure access to instances in a private subnet.

| Aspect | Description |
|--------|-------------|
| **Purpose** | Single entry point for administrators to access private subnet instances. |
| **Location** | Launched in a **public subnet** (with a public IP or Elastic IP). |
| **Security** | Restrict SSH/RDP access to known IPs (e.g., corporate office, VPN). |
| **Access flow** | Admin → Bastion Host → Private EC2 Instance. |

**Why we need it:** Private subnet instances have no public IP and cannot be accessed from the internet. The bastion host is the only entry point.

**HA architecture:**

To make the bastion host highly available:
- Launch a bastion host in **each AZ** (behind an Auto Scaling Group with min/max = 1).
- Use an **NLB** or **Elastic IP** to reach the bastion.
- Or use **AWS Systems Manager Session Manager** (no bastion host needed – recommended modern approach).

**Use cases:**
- SSH access to private EC2 instances.
- RDP access to private Windows instances.
- Administering databases in private subnets.

**Bastion host alternatives (modern):**
- **AWS Systems Manager Session Manager** – no bastion host, no SSH keys, audited via CloudTrail.
- **AWS Client VPN** – managed VPN for remote access.
- **Direct Connect + VPN** – for corporate access.

## 6. Project 2 – Requirements 1 & 2

**Project 2:** Design a solution for a two‑tier web application for a client on AWS. The solution must be highly available and fault tolerant within a single AWS Region. The application tiers will be deployed using EC2 instances.

**Requirement 1:** The database servers must not be accessible from the internet. However, they need to access the internet for updates and security patches.

**Design decisions:**
- Deploy database servers in **private subnets** (no public IP).
- Create a **NAT Gateway** in the public subnet.
- Update the private subnet's route table to point `0.0.0.0/0` to the NAT Gateway.
- The database servers can now reach the internet for updates without being accessible from the internet.

**Requirement 2:** Database administrators from the corporate network need SSH access to administer the database EC2 instances. This access should only be allowed from the corporate data center.

**Design decisions:**
- Deploy a **Bastion Host** in a public subnet (restricted to the corporate IP range).
- Or use **AWS Systems Manager Session Manager** (no bastion, no open SSH port).
- Or use a **VPN connection** from the corporate network to the VPC.
- Security Group on the database EC2 instances: allow SSH (port 22) **only from the bastion host's Security Group** (or corporate IP range).

**Solution architecture:**

```
Corporate Network
        │
        ▼
┌───────────────────────────────────────────────────────────────────┐
│  VPC (10.0.0.0/16)                                                │
│                                                                   │
│  ┌─────────────────────────────────────────────────────────────┐  │
│  │  Public Subnet (10.0.10.0/24)                               │  │
│  │  ┌───────────────┐  ┌───────────────┐                       │  │
│  │  │ Bastion Host  │  │ NAT Gateway   │                       │  │
│  │  └───────────────┘  └───────────────┘                       │  │
│  └─────────────────────────────────────────────────────────────┘  │
│                                                                   │
│  ┌─────────────────────────────────────────────────────────────┐  │
│  │  Private Subnet (10.0.100.0/24)                             │  │
│  │  ┌─────────────────────────────────────────────────────────┐│  │
│  │  │ Database EC2 Instances (No Public IP)                    ││  │
│  │  │ Access: SSH from Bastion only                            ││  │
│  │  │ Internet: Via NAT Gateway (outbound only)                ││  │
│  │  └─────────────────────────────────────────────────────────┘│  │
│  └─────────────────────────────────────────────────────────────┘  │
└───────────────────────────────────────────────────────────────────┘
```

## 7. VPC Peering

**VPC Peering** allows routing between two VPCs as if they were on the same network.

**By default, VPCs cannot communicate with each other.** VPC Peering establishes a connection.

| Aspect | Description |
|--------|-------------|
| **Accounts** | Both VPCs can be in the same AWS account or different accounts. |
| **Regions** | Both VPCs can be in the same Region or different Regions (inter‑region peering). |
| **CIDR requirement** | The two VPCs **cannot have overlapping CIDR ranges**. |
| **Route tables** | You must update route tables in both VPCs to route traffic to the peering connection. |

### Transitive Peering (NOT Supported)

If VPC A is peered with VPC B, and VPC B is peered with VPC C, VPC A **cannot** communicate with VPC C through VPC B. Each peering connection is isolated.

```
VPC A ←→ VPC B ←→ VPC C

VPC A cannot reach VPC C through VPC B.
```

### Edge‑to‑Edge Routing (NOT Supported)

You cannot route traffic through a VPC peering connection to a VPN, Direct Connect, or Internet Gateway attached to the peer VPC.

**Example:** VPC A has a VPN connection to on‑premises. VPC B is peered with VPC A. VPC B **cannot** reach on‑premises through VPC A's VPN.

### AWS VPC Peering – Scaling Limitations

- You must create a peering connection for each pair of VPCs.
- If you have 10 VPCs, you need up to 45 peering connections (10 × 9 / 2) for full mesh.
- This becomes unmanageable at scale – which is why **AWS Transit Gateway** was created.

## 8. AWS Transit Gateway

**AWS Transit Gateway** is a central hub that connects multiple VPCs and on‑premises networks.

**Problem it solves:** VPC Peering requires a connection for each pair of VPCs (full mesh), which does not scale. Transit Gateway acts as a hub‑and‑spoke model.

```
        VPC A
          │
          ▼
VPC B ←→ Transit Gateway ←→ VPC C
          ▲
          │
    On-Premises (VPN/Direct Connect)
```

| Aspect | Description |
|--------|-------------|
| **Hub‑and‑spoke** | Connect many VPCs to a single Transit Gateway. |
| **Transitive routing** | VPC A can reach VPC C through the Transit Gateway. |
| **On‑premises** | Connect VPN or Direct Connect to the Transit Gateway. |
| **Inter‑Region** | Transit Gateway can peer with other Transit Gateways in different Regions. |
| **Scalability** | Supports thousands of VPCs. |
| **Use case** | Large organisations with many VPCs and on‑premises connectivity. |

**Transit Gateway vs. VPC Peering:**

| Feature | VPC Peering | Transit Gateway |
|---------|-------------|-----------------|
| **Topology** | Full mesh (point‑to‑point). | Hub‑and‑spoke. |
| **Transitive routing** | No. | Yes. |
| **Scaling** | Poor (many connections needed). | Excellent (single hub). |
| **Cost** | No hourly charge for peering. | Hourly charge per attachment + data processing. |
| **Use case** | Simple, few VPCs. | Complex, many VPCs, hybrid connectivity. |

## 9. VPC Endpoints

**VPC Endpoints** allow you to privately connect your VPC to supported AWS services **without using the internet**, NAT, VPN, or Direct Connect.

**Why we need them:**
- Keep traffic **within the AWS network** (not over the public internet).
- Improve security (no exposure to the internet).
- Reduce NAT Gateway data processing costs.

### Two Types of VPC Endpoints

| Type | Description | Supported Services |
|------|-------------|---------------------|
| **Gateway Endpoint** | A gateway that is a target for a route in your route table. | **S3** and **DynamoDB** only. |
| **Interface Endpoint** | An elastic network interface (ENI) with a private IP address in your subnet. Powered by AWS PrivateLink. | Most AWS services (EC2, SNS, SQS, KMS, etc.). |

### Interface Endpoint vs. Gateway Endpoint

| Feature | Gateway Endpoint | Interface Endpoint |
|---------|------------------|---------------------|
| **Supported services** | S3, DynamoDB only. | Most AWS services. |
| **Implementation** | Route table entry (prefix list). | ENI with private IP. |
| **Cost** | Free. | Hourly charge + data processing. |
| **Access from on‑premises** | Not directly. | Yes (via VPN/Direct Connect). |
| **Security** | Controlled by endpoint policy. | Controlled by Security Group + endpoint policy. |
| **DNS** | Uses public DNS with private routing. | Uses private DNS (optional). |

### Services That Support Endpoints

Most AWS services support VPC endpoints. Examples:
- **S3** (Gateway)
- **DynamoDB** (Gateway)
- **EC2, ECS, EKS** (Interface)
- **SNS, SQS, KMS, Secrets Manager** (Interface)
- **CloudWatch, CloudTrail** (Interface)

### Services Inside vs. Outside the VPC

| Service Location | Access Method |
|------------------|---------------|
| **Inside the VPC** | Direct (private IPs). |
| **Outside the VPC** | VPC Endpoint (private), or NAT Gateway / IGW (public). |

### Accessing VPC Endpoints from Remote Networks Using Proxy Server

For on‑premises access to VPC endpoints (via VPN or Direct Connect), you may need a **proxy server** to resolve DNS and route traffic to the endpoint's private IP.

### Controlling Access to Services with VPC Endpoint Policies

VPC Endpoint Policies are JSON documents that control which resources can be accessed through the endpoint.

**Example – Restrict S3 access to a specific bucket:**

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": "*",
            "Action": "s3:*",
            "Resource": "arn:aws:s3:::my-bucket/*"
        }
    ]
}
```

## 10. Project 2 – Requirements 3 & 4

**Requirement 3:** Access to the database should be limited to the application tier and the administration traffic. Any other access should not be allowed.

**Design decisions:**
- **Security Group** on database EC2 instances:
  - Inbound: allow database port (e.g., 3306 for MySQL) **only from the application tier's Security Group**.
  - Inbound: allow SSH (22) **only from the bastion host's Security Group**.
  - Implicit deny for all other traffic.
- **NACL** on the private subnet: allow database traffic only from the application subnet and administrative traffic from the bastion subnet.

**Requirement 4:** Database servers will need to store data in S3. This traffic should not traverse the internet.

**Design decisions:**
- Create a **Gateway VPC Endpoint** for S3.
- Update the private subnet's route table to route S3 traffic (`pl-xxxxxxx` prefix list) to the VPC Endpoint.
- The database servers can now access S3 privately without traversing the internet or NAT Gateway.

**Architecture addition:**

```
Private Subnet → Route Table → S3 Gateway Endpoint → S3 (private)
```

## 12. Practice Lab – Verify Your Understanding

1. **NAT Gateway (hands‑on):**
   - Create a NAT Gateway in a public subnet.
   - Allocate an Elastic IP.
   - Update a private subnet's route table to point `0.0.0.0/0` to the NAT Gateway.
   - Launch an EC2 instance in the private subnet and verify it can reach the internet (e.g., `curl google.com`) but cannot be reached from the internet.

2. **Bastion Host (hands‑on):**
   - Launch a bastion host in a public subnet.
   - Restrict SSH access to your IP.
   - Use SSH agent forwarding to connect to a private EC2 instance: `ssh -A ec2-user@bastion` then `ssh ec2-user@private-ip`.

3. **VPC Peering (hands‑on):**
   - Create two VPCs with non‑overlapping CIDRs.
   - Create a peering connection.
   - Update route tables in both VPCs.
   - Test connectivity between instances in both VPCs.

4. **Transit Gateway (hands‑on):**
   - Create a Transit Gateway.
   - Attach two VPCs to it.
   - Update route tables.
   - Test connectivity between VPCs (transitive).

5. **VPC Endpoint for S3 (hands‑on):**
   - Create a Gateway VPC Endpoint for S3.
   - Update the private subnet's route table.
   - Verify an EC2 instance in the private subnet can access S3 without a NAT Gateway.

6. **Project 2 implementation:**
   - Implement the full architecture:
     - VPC with public and private subnets (two AZs).
     - Bastion host in a public subnet.
     - NAT Gateway for private subnet internet access.
     - Database EC2 instances in private subnets (no public IP).
     - Security Groups: database access only from the app tier and bastion.
     - S3 Gateway Endpoint for private S3 access.
     - Multi‑AZ for high availability.
