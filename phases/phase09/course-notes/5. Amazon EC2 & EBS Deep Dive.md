## 1. AWS IPv6 Egress‑Only Internet Gateway

An **Egress‑Only Internet Gateway** is a VPC component that allows outbound IPv6 traffic from your VPC to the internet, while preventing the internet from initiating connections to your IPv6 resources.

| Characteristic | Description |
|----------------|-------------|
| **IPv6 addresses** | All IPv6 addresses are public (no NAT for IPv6). |
| **Purpose** | Allows IPv6 traffic to leave the VPC but blocks inbound connections from the internet. |
| **Statefulness** | Stateful – return traffic is automatically allowed. |
| **Security Groups** | Cannot be associated with a Security Group. |
| **Use case** | Private subnets with IPv6 that need outbound internet access (updates, patches). |
| **Analogy** | Similar to NAT Gateway, but for IPv6. |

**How it works:**

```
Private Subnet (IPv6) → Egress-Only IGW → Internet (outbound only)
Internet → Egress-Only IGW → Blocked (inbound denied)
```

**Route table configuration:** Add a route for `::/0` pointing to the Egress‑Only Internet Gateway.

## 2. VPC Flow Logs

**VPC Flow Logs** is a feature that captures information about IP traffic going to and from network interfaces in your VPC.

| Characteristic | Description |
|----------------|-------------|
| **Purpose** | Capture source IP/port, destination IP/port, protocol, and status (ACCEPT/REJECT). |
| **Scope** | Per VPC, per subnet, or per ENI (Elastic Network Interface). |
| **Destinations** | CloudWatch Logs or S3. |
| **Use cases** | Troubleshooting connectivity, security analysis, monitoring traffic patterns. |
| **Does not capture** | DNS traffic (if using Route 53 Resolver), DHCP traffic, instance metadata traffic. |

**Example flow log entry:**

```
2 123456789012 eni-abc123 10.0.1.5 10.0.2.10 443 12345 6 10 840 1620140761 1620140821 ACCEPT OK
```

| Field | Meaning |
|-------|---------|
| `2` | Version |
| `123456789012` | Account ID |
| `eni-abc123` | ENI ID |
| `10.0.1.5` | Source IP |
| `10.0.2.10` | Destination IP |
| `443` | Destination port |
| `12345` | Source port |
| `6` | Protocol (TCP) |
| `10` | Packets |
| `840` | Bytes |
| `1620140761` | Start time |
| `1620140821` | End time |
| `ACCEPT` | Action (ACCEPT/REJECT) |
| `OK` | Log status |

**Why VPC Flow Logs matter for the exam:** They are used for **security auditing**, **troubleshooting connectivity issues** (e.g., why is traffic being rejected?), and **compliance**.

## 3. Hybrid Cloud Networking on AWS

### 3.1 TCP/IP Routing – Static and Dynamic

**IP routing** is about routers exchanging their reachable network knowledge so that every router knows about all networks and how to reach them.

| Routing Type | Description | When to Use |
|--------------|-------------|-------------|
| **Static Routing** | Routes are manually configured. | Simple, small networks. |
| **Dynamic Routing** | Routers exchange routes using protocols like **BGP** (Border Gateway Protocol). | Large, complex networks, automatic failover. |

**AWS supports BGP** for dynamic routing in VPN and Direct Connect.

### 3.2 IPsec

**IPsec (Internet Protocol Security)** is a secure network‑layer protocol suite that authenticates and encrypts data packets between:
- Host and host
- Host and gateway
- Gateway to gateway (site‑to‑site)

| Characteristic | Description |
|----------------|-------------|
| **Layer** | Layer 3 (Network layer). |
| **Use** | VPNs (secure communication over the internet). |
| **Not end‑to‑end** | Only encrypts between the two VPN endpoints (not from client to server). |
| **Cost** | Low – uses the public internet. |
| **Latency** | High – depends on internet conditions. |
| **Setup** | Fast – can be deployed in minutes. |

### 3.3 AWS Managed VPNs

AWS provides a **managed VPN** service for connecting your on‑premises network to your VPC.

| Component | Description |
|-----------|-------------|
| **Virtual Private Gateway (VPG)** | Attached to the VPC – the AWS side of the VPN. |
| **Customer Gateway (CGW)** | Your on‑premises router/firewall – the customer side. |
| **VPN Connection** | Two IPsec tunnels for redundancy. |

**Two tunnels are provided for high availability** – if one fails, traffic fails over to the other.

### 3.4 AWS Direct Connect (DX)

**Direct Connect** is a private, dedicated network connection between your on‑premises data centre and AWS.

| Characteristic | Description |
|----------------|-------------|
| **Network** | Private – not over the public internet. |
| **Bandwidth** | 1 Gbps, 10 Gbps, 100 Gbps. |
| **Latency** | Low – consistent. |
| **Setup time** | Weeks to months (long lead time). |
| **Cost** | High – port fees + data transfer. |
| **VIF (Virtual Interface)** | A private VIF connects to a VPC; a public VIF connects to AWS public endpoints. |

**VIF Types:**

| VIF Type | Connects To | Use Case |
|----------|-------------|----------|
| **Private VIF** | VPC (Virtual Private Gateway) | Access private resources in a VPC. |
| **Public VIF** | AWS public endpoints (S3, DynamoDB, etc.) | Access AWS public services privately. |
| **Transit VIF** | Transit Gateway | Connect to multiple VPCs via Transit Gateway. |

**802.1Q Trunk:** Direct Connect supports VLAN tagging (802.1Q) to carry multiple VIFs over a single physical connection.

### 3.5 Direct Connect Gateway

**Direct Connect Gateway** allows you to connect a single Direct Connect connection to multiple VPCs in different AWS Regions.

| Feature | Description |
|---------|-------------|
| **Purpose** | Connect on‑premises to multiple VPCs across Regions. |
| **Association** | Associate with up to 10 Virtual Private Gateways (VPGs). |
| **Use case** | Global hybrid cloud architecture. |

**Without Direct Connect Gateway:** You need a separate Direct Connect connection for each VPC (expensive and complex).

**With Direct Connect Gateway:** One connection, many VPCs.

### 3.6 High Availability for Hybrid Connectivity

| Scenario | Solution |
|----------|----------|
| **Redundant VPN tunnels** | AWS provides two tunnels per VPN connection. |
| **Redundant Direct Connect** | Use two Direct Connect connections from different locations. |
| **Backup connection** | Use a VPN as a backup for Direct Connect (or vice versa). |
| **Direct Connect + VPN** | Direct Connect as primary, VPN as backup. |

**Best practice:** For high availability, use **two Direct Connect connections** from different providers/locations, or **Direct Connect + VPN**.

## 4. EC2 Instance Types and Families

EC2 instances are categorised by **family** based on their compute, memory, storage, and networking characteristics.

| Family Category | Prefix | Description | Use Cases |
|-----------------|--------|-------------|-----------|
| **General Purpose** | `A`, `M`, `T` | Balanced CPU, memory, and networking. | Web servers, small/medium databases, dev/test. |
| **Compute Optimized** | `C` | More CPU than memory. | Batch processing, media transcoding, HPC, gaming, scientific modelling. |
| **Memory Optimized** | `R`, `U`, `X`, `Z` | More RAM. | In‑memory databases (Redis), real‑time big data analytics, high‑performance databases. |
| **Storage Optimized** | `I`, `D`, `H` | High disk throughput (local NVMe/SSD). | Data warehousing, distributed file systems, Hadoop. |
| **Accelerated Computing** | `P`, `G`, `F`, `Inf`, `Trn` | GPU/FPGA‑based. | Machine learning, graphics rendering, video encoding. |

**Instance Type Naming Convention:**

```
M5.large
│ │  │
│ │  └── Size (large, xlarge, 2xlarge, etc.)
│ └── Generation (5 = 5th generation)
└── Family (M = general purpose)
```

**Example:** `M4.large` – General purpose, 4th generation, large size.

## 5. EC2 Instance Lifecycle

| State | Description | Billing |
|-------|-------------|---------|
| **Pending** | Instance is launching. | Not billed. |
| **Running** | Instance is active. | **Billed** (per second, minimum 60 seconds). |
| **Rebooting** | Instance is restarting. | **Billed** (treated as running). |
| **Stopping** | Instance is shutting down. | Not billed (for EBS‑backed). |
| **Stopped** | Instance is shut down. | Not billed (EBS charges still apply). |
| **Stop‑Hibernating** | Instance is being hibernated. | **Billed** during hibernation. |
| **Terminated** | Instance is permanently deleted. | Not billed (EBS charges may apply). |

**Hibernation:** Saves the instance's RAM contents to EBS, allowing faster restart. Available for certain instance families (e.g., `t3`, `m5`).

## 6. EC2 Instance Metadata & User Data

### Instance Metadata

**Instance metadata** is data about your EC2 instance that you can access from within the instance.

| Endpoint | Description |
|----------|-------------|
| `http://169.254.169.254/latest/meta-data/` | Instance metadata (instance ID, IP, AMI, etc.). |
| `http://169.254.169.254/latest/user-data/` | User data (launch script). |

**Examples:**

```bash
# Get instance ID
curl http://169.254.169.254/latest/meta-data/instance-id

# Get public IP
curl http://169.254.169.254/latest/meta-data/public-ipv4

# Get user data
curl http://169.254.169.254/latest/user-data
```

> **Note:** IMDSv2 (Instance Metadata Service v2) uses a token‑based approach for better security. IMDSv1 is deprecated.

### User Data

**User Data** is a script that runs when an instance first launches. It is used to automate configuration (e.g., install packages, start services).

**Example user data script (bash):**

```bash
#!/bin/bash
yum update -y
yum install -y httpd
systemctl start httpd
systemctl enable httpd
echo "Hello from EC2" > /var/www/html/index.html
```

**User data runs once** at launch (by default). To re‑run it, you must configure it differently or use a tool like `cloud-init`.

## 7. EC2 Purchasing/Launch Options

| Option | Description | Discount | Commitment | Use Case |
|--------|-------------|----------|------------|----------|
| **On‑Demand** | Pay by the second. | 0% (most expensive) | None | Short‑term, unpredictable workloads. |
| **Reserved (Standard)** | 1 or 3 years. Zonal or regional. | Up to 75% | 1 or 3 years | Steady‑state, predictable workloads. |
| **Reserved (Convertible)** | 1 or 3 years. Can change instance family. | Up to 54% | 1 or 3 years | Predictable workloads with possible changes. |
| **Scheduled Reserved** | 1 year. Recurring schedule (daily, weekly). | Up to 54% | 1 year | Recurring workloads (e.g., nightly batch). |
| **Spot** | Bid on spare capacity. Can be interrupted. | Up to 90% | None | Fault‑tolerant, flexible workloads. |
| **Savings Plans** | Commit to a spend amount ($/hour) for 1 or 3 years. | Up to 72% | 1 or 3 years | Flexible across instance families and Regions. |
| **Dedicated Hosts** | Physical server dedicated to you. | Varies | On‑Demand or Reserved | Compliance, licensing (Windows, Oracle). |
| **Dedicated Instances** | Instances on hardware dedicated to you. | Varies | On‑Demand | Compliance, but not full host control. |

**Key differences:**

- **Standard RI:** Fixed instance family, can change AZ (regional) or size (within family).
- **Convertible RI:** Can change instance family, OS, tenancy.
- **On‑Demand Capacity Reservation:** Reserve capacity without a long‑term commitment (no discount).
- **Dedicated Host:** You get the entire physical server (visibility into sockets, cores, host ID).
- **Dedicated Instance:** You get instances on dedicated hardware, but not the entire host.

## 8. EC2 Spot Instances

**Spot Instances** let you bid on unused EC2 capacity at up to 90% discount.

| Characteristic | Description |
|----------------|-------------|
| **Best for** | Fault‑tolerant, flexible workloads (batch jobs, data analysis, CI/CD). |
| **Can be interrupted** | AWS can reclaim the instance with a 2‑minute warning. |
| **Spot Request** | Defines max price, number of instances, specifications. |
| **Spot Fleet** | A collection of Spot Instances (and optionally On‑Demand) to meet target capacity. |

**Spot Request Types:**

| Type | Description |
|------|-------------|
| **One‑Time** | The request is fulfilled once; the instance runs until interrupted or terminated. |
| **Persistent** | The request remains active; if the instance is interrupted, a new one is launched. |

**Spot Block:** Request Spot Instances for a specified duration (1–6 hours) without interruption.

**Spot Interruption:** AWS sends a 2‑minute warning before reclaiming the instance. You can handle it with:
- **Checkpointing** – save state periodically.
- **Diversification** – use multiple instance types and AZs.
- **Spot Fleet** – automatically replace interrupted instances.

## 9. EC2 Placement Groups

**Placement Groups** control how instances are placed on underlying hardware.

| Placement Group Type | Description | Use Case |
|----------------------|-------------|----------|
| **Cluster** | Instances are placed in a single AZ, close together. | HPC, low‑latency inter‑node communication. |
| **Partition** | Instances are spread across partitions (logical segments of racks). | Distributed workloads (Hadoop, Cassandra, Kafka). |
| **Spread** | Instances are placed on distinct hardware (separate racks). | Critical applications, small number of instances. |

**Cluster Placement Group:**

- Single AZ.
- Low latency (high‑speed network between instances).
- Cannot span AZs.
- Use for HPC that requires low latency.

**Partition Placement Group:**

- Instances are divided into partitions (max 7 per AZ).
- Instances in one partition do not share hardware with other partitions.
- Good for large distributed workloads (HDFS, Cassandra).

**Spread Placement Group:**

- Instances are placed on distinct hardware (max 7 per AZ).
- Reduces risk of simultaneous failure.
- Good for a small number of critical instances.

## 10. EC2 Instance Billing

| State | Billed? | Notes |
|-------|---------|-------|
| **Running** | ✅ Yes | Per second (minimum 60 seconds). |
| **Rebooting** | ✅ Yes | Treated as running. |
| **Stopping** | ✅ Yes | During hibernation (stop‑hibernate). |
| **Stopped** | ❌ No | EBS charges still apply. |
| **Terminated** | ❌ No | EBS charges may apply if volumes are not deleted. |

**Data transfer costs:**
- **Inbound:** Free.
- **Outbound:** Charged (per GB).
- **Between AZs:** Charged (both directions).
- **Within the same AZ:** Free (if using private IPs).

## 11. EC2 Monitoring

### EC2 Status Checks

| Status Check | Description | Who Fixes |
|--------------|-------------|-----------|
| **System Status Check** | Detects issues with the underlying host (hardware, network, power). | AWS |
| **Instance Status Check** | Detects issues with the instance (misconfiguration, OS issues). | Customer |

Both checks run every **minute** by default. Results: `ok` or `impaired`.

### CloudWatch Monitoring

| Monitoring Type | Frequency | Cost | Use Case |
|-----------------|-----------|------|----------|
| **Basic Monitoring** | Every 5 minutes | Free | Default monitoring. |
| **Detailed Monitoring** | Every 1 minute | Chargeable | Production workloads, faster response. |

**Default EC2 Metrics:**
- CPU utilisation
- Network in/out
- Disk reads/writes
- Status check failures

**Custom Metrics:** You can push your own metrics (e.g., memory usage, application‑specific metrics) using the CloudWatch agent.

### CloudWatch Alarms and Events

| Action | Description |
|--------|-------------|
| **Recover** | Recover an instance from a system status check failure. |
| **Reboot** | Reboot an instance on an instance status check failure. |
| **Stop** | Stop an instance. |
| **Terminate** | Terminate an instance. |

**CloudWatch Events:** Respond automatically to events (e.g., EC2 state changes, API calls).

## 12. Elastic Block Store (EBS)

**EBS (Elastic Block Store)** is persistent block storage for EC2 instances.

| Characteristic | Description |
|----------------|-------------|
| **Type** | Block storage (like a raw unformatted hard drive). |
| **Persistence** | Data persists after instance stop/termination. |
| **Replication** | Data is replicated across multiple servers in the same AZ. |
| **Attachment** | Attaches to a single EC2 instance at a time (through the AWS network). |
| **AZ Requirement** | Both the instance and the EBS volume must be in the **same AZ**. |
| **Use case** | Operating systems, databases, application data. |

**EBS vs. Instance Store:**

| Feature | EBS | Instance Store |
|---------|-----|----------------|
| **Persistence** | Persistent | Ephemeral (lost on stop/termination). |
| **Location** | Network‑attached | Physically attached to host. |
| **Speed** | Slower (network) | Faster (local). |
| **IOPS** | Up to 64,000 | Millions of IOPS. |
| **Use case** | Databases, file systems. | Caches, buffers, scratch data. |

---

## 13. EC2 Instance Store

**Instance Store** provides temporary block‑level storage for EC2 instances.

| Characteristic | Description |
|----------------|-------------|
| **Persistence** | Ephemeral – data is lost when the instance is stopped or terminated. |
| **Location** | Physically attached to the host (local NVMe/SSD). |
| **Speed** | Very fast – millions of IOPS. |
| **Use cases** | Buffers, caches, scratch data, temporary files. |
| **Availability** | Not all instance types include instance store. |

---

## 14. EBS Volume Types

| Volume Type | Category | Description | Use Case |
|-------------|----------|-------------|----------|
| **gp2** | SSD (General Purpose) | Older SSD type. Burst performance. | Boot volumes, dev/test. |
| **gp3** | SSD (General Purpose) | Newer SSD type. Baseline 3,000 IOPS, 125 MB/s. Can provision higher IOPS/throughput independently. | Boot volumes, most workloads. |
| **io1** | SSD (Provisioned IOPS) | High‑performance SSD. Up to 64,000 IOPS. | Databases, latency‑sensitive workloads. |
| **io2** | SSD (Provisioned IOPS) | Next‑gen io1. Up to 64,000 IOPS, 99.999% durability. | Mission‑critical databases. |
| **st1** | HDD (Throughput Optimized) | Low‑cost HDD for sequential workloads. | Big data, data warehouses, log processing. |
| **sc1** | HDD (Cold) | Lowest‑cost HDD for infrequent access. | Archive, cold data. |

**Choosing between SSD and HDD:**

| Workload | Recommended |
|----------|-------------|
| Random I/O, consistent performance | **SSD** (gp2, gp3, io1, io2) |
| Large sequential I/O, throughput | **HDD** (st1, sc1) |

## 16. Practice Lab – Verify Your Understanding

1. **User Data:**
   - Launch an EC2 instance with user data that installs Apache and starts it.
   - Verify the web server is running by accessing the public IP.

2. **Instance Metadata:**
   - Connect to an EC2 instance and run `curl http://169.254.169.254/latest/meta-data/instance-id`.
   - Retrieve the public IP and AMI ID.

3. **Spot Instance:**
   - Request a Spot Instance with a maximum price.
   - Simulate an interruption and observe the 2‑minute warning.

4. **Placement Group:**
   - Create a Cluster placement group and launch two instances in it.
   - Test inter‑node latency.

5. **EBS:**
   - Create a `gp3` volume and attach it to an EC2 instance.
   - Format and mount it.
   - Take a snapshot and create a new volume from it.

6. **EBS Volume Types:**
   - Create an `io2` volume (provisioned IOPS) and attach it to a database instance.
   - Create an `st1` volume (throughput optimized HDD) for log data.

7. **VPC Flow Logs:**
   - Create a flow log for a VPC.
   - Generate traffic (e.g., SSH to an instance).
   - View the flow log entries in CloudWatch Logs.

   - Explain the difference between a private VIF and a public VIF.
