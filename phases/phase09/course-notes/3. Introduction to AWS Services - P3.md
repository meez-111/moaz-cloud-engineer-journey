## 1. IAM Access Keys – Programmatic Access

### Methods to Access AWS Services

| Access Method | Credentials | Use Case |
|---------------|-------------|----------|
| **Console access** | Username + password | AWS Management Console (web UI). |
| **Programmatic access** | Access Key ID + Secret Access Key | CLI, SDK, API calls, automation. |

### Access Keys

| Characteristic | Description |
|----------------|-------------|
| **Purpose** | Used to make programmatic calls to AWS services (CLI, SDK, API). |
| **Management** | Access keys can be created, modified, viewed, or rotated. |
| **Secret key** | **The secret access key is accessible only at the time of creation.** Download and store it securely (you cannot retrieve it later). |
| **CLI configuration** | To use the AWS CLI, you must configure your laptop with access keys before sending requests. |

**Security best practices:**
- **Never share your secret access key.**
- **Rotate keys regularly** (e.g., every 90 days).
- **Delete unused keys** (if you're not using a key, remove it).
- **Use IAM roles instead of access keys for EC2 instances** and other AWS services.

## 2. AWS IAM – Elements and Policies

### IAM Elements

| Element | Description |
|---------|-------------|
| **Principal** | The entity making the request (user, role, federated user, application). |
| **Authentication** | How the principal proves its identity (password, access keys, MFA). |
| **Request** | The API call being made (e.g., `ec2:DescribeInstances`). |
| **Authorization** | The process of determining if the principal is allowed to perform the request. |
| **Policy** | A document (JSON) that defines permissions. |
| **Permissions** | The specific actions and resources allowed or denied. |
| **Actions** | The operations the principal can perform (e.g., `s3:GetObject`). |
| **Resources** | The AWS resources the principal can access (e.g., `arn:aws:s3:::my-bucket`). |

**Cross‑account access:** IAM allows you to grant permissions to principals from other AWS accounts. You can do this by creating an IAM role in your account and allowing principals from another account to assume that role.

### IAM Policy Types

| Policy Type | Description |
|-------------|-------------|
| **AWS Managed Policies** | Pre‑defined policies created by AWS (e.g., `AdministratorAccess`, `ReadOnlyAccess`). |
| **Customer Managed Policies** | Policies you create and manage yourself. |
| **Inline Policies** | Policies that are embedded directly into a user, group, or role (not reusable). |

**Identity‑based vs. Resource‑based Policies:**

| Type | Attached To | Example |
|------|-------------|---------|
| **Identity‑based** | User, group, or role. | `AdministratorAccess` attached to a user. |
| **Resource‑based** | The resource itself (e.g., S3 bucket policy, SQS queue policy). | S3 bucket policy granting public read access. |

**Policies are JSON documents:**

```json
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": "s3:GetObject",
            "Resource": "arn:aws:s3:::my-bucket/*"
        }
    ]
}
```

## 3. EC2 IAM Roles

**IAM Roles** are the recommended way to grant permissions to AWS services (like EC2) instead of embedding access keys directly.

**Why use IAM roles for EC2?**

| Aspect | IAM Role (Best Practice) | Access Keys (Not Recommended) |
|--------|---------------------------|-------------------------------|
| **Security** | Temporary credentials (rotated automatically). | Long‑term credentials (stored on the instance). |
| **Management** | No need to rotate or manage keys. | Must rotate keys manually. |
| **Audit** | Actions are logged as coming from the role. | Harder to trace who used the keys. |

**Creating and attaching an IAM role to an EC2 instance:**

1. Create a role in IAM with the required permissions (e.g., `AmazonS3ReadOnlyAccess`).
2. Assign the role to the EC2 instance at launch (or attach it to an existing instance via the console/CLI).
3. The EC2 instance can now access AWS services using the role's permissions – no access keys required.

## 4. Monolithic vs. Multi‑Tier Applications

| Aspect | Monolithic | Multi‑Tier |
|--------|------------|------------|
| **Definition** | All application components are bundled into a single codebase. | Application is split into separate tiers (web, app, database). |
| **Deployment** | Deployed as a single unit. | Each tier can be deployed, scaled, and managed independently. |
| **Scalability** | Scale the entire application (not efficient). | Scale individual tiers (web tier separately from database). |
| **Maintenance** | Changes affect the entire application. | Changes are isolated to a specific tier. |
| **Example** | A single JAR file with everything. | Web servers (tier 1), application servers (tier 2), database (tier 3). |

**Multi‑tier architecture is the foundation of cloud‑native applications.** It allows you to decouple components, scale independently, and improve resilience.

## 5. Introduction to Messaging and Notification Services

### 5.1 SQS – Simple Queue Service

**SQS** is a fully managed message queuing service that enables you to decouple and scale microservices, distributed systems, and serverless applications.

| Characteristic | Description |
|----------------|-------------|
| **Purpose** | Decouple application components by passing messages between them. |
| **Communication** | Asynchronous – sender and receiver do not need to be active at the same time. |
| **Queue types** | Standard (best‑effort ordering, at‑least‑once delivery) and FIFO (first‑in, first‑out, exactly‑once). |
| **Persistence** | Messages are stored in the queue until they are consumed (or expire). |
| **Use case** | Order processing, task queuing, decoupling web and backend tiers. |

### 5.2 SNS – Simple Notification Service

**SNS** is a fully managed Pub/Sub messaging service that enables you to send notifications to multiple subscribers.

| Characteristic | Description |
|----------------|-------------|
| **Purpose** | Send notifications to a large number of subscribers (push model). |
| **Communication** | Asynchronous – publisher sends messages to a topic, subscribers receive them. |
| **Subscriber types** | Email, SMS, SQS queues, Lambda functions, HTTP/HTTPS endpoints, mobile push. |
| **Use case** | Alerting, event‑driven architectures, fan‑out patterns. |

### 5.3 SQS vs. SNS

| Feature | SQS | SNS |
|---------|-----|-----|
| **Pattern** | Point‑to‑point (queue). | Pub/Sub (topic). |
| **Consumer** | One consumer (or multiple in a competing consumer pattern). | Many subscribers (fan‑out). |
| **Delivery** | Pull‑based (consumer polls the queue). | Push‑based (messages are pushed to subscribers). |
| **Ordering** | Standard: best‑effort; FIFO: guaranteed. | Ordering is not guaranteed. |
| **Use case** | Decouple components, task queues. | Notifications, alerts, fan‑out to multiple services. |

## 6. Project 1 – Requirement 4

**Requirement 4:** Administrators and developers will need programmatic access to AWS services. Moreover, the application on EC2 instances will require access to AWS services.

**Design decisions:**

| User/Component | Access Method | Recommended Approach |
|----------------|---------------|----------------------|
| **Administrators** | Programmatic access (CLI, SDK). | Create IAM users with appropriate policies (e.g., `AdministratorAccess`). Enable MFA. Use access keys for CLI. |
| **Developers** | Programmatic access (CLI, SDK). | Create IAM users with developer policies (e.g., limited to specific services). Enable MFA. |
| **EC2 Application** | Access to AWS services (e.g., S3, DynamoDB). | **IAM Role** – attach a role to the EC2 instance with the required permissions. **Do not** use access keys on EC2. |

**Why IAM roles for EC2?**
- No need to store access keys on the instance.
- Credentials are rotated automatically.
- Auditable via CloudTrail.

## 7. Amazon CloudFront (CDN) 101

**Amazon CloudFront** is a **Content Delivery Network (CDN)** that accelerates the delivery of static and dynamic web content by caching it at **edge locations** around the world.

### Without CloudFront – Simple Use Case

```
User → Origin Server (e.g., EC2, S3)
```

- Users access content directly from the origin server.
- High latency for users far from the origin.
- Additional load on the origin server.

### With CloudFront

```
User → Edge Location (CloudFront) → Origin Server
```

- Content is cached at edge locations closest to users.
- Low latency for global users.
- Reduced load on the origin server.

### Edge Locations

- CloudFront has **550+ edge locations** worldwide.
- Edge locations are data centres that cache content.
- If the content is not cached, CloudFront fetches it from the **origin** and caches it at the edge.

**Use cases:**
- Static websites (S3 + CloudFront).
- Dynamic content acceleration (API responses, video streaming).
- DDoS protection (CloudFront is integrated with AWS Shield).

## 8. Amazon Route 53 101

**Amazon Route 53** is a highly available and scalable Domain Name System (DNS) web service.

### What is DNS?

**DNS (Domain Name System)** translates human‑readable domain names (e.g., `www.example.com`) into IP addresses (e.g., `192.0.2.10`).

### Amazon Route 53 Features

| Feature | Description |
|---------|-------------|
| **Domain registration** | Register domain names directly through AWS. |
| **DNS resolution** | Route 53 responds to DNS queries with the correct IP address. |
| **Health checks** | Monitor the health of endpoints (EC2, ALB, S3). |
| **Routing policies** | Simple, weighted, latency‑based, geolocation, failover, multi‑value. |
| **Private hosted zones** | DNS resolution within your VPCs (not exposed to the internet). |
| **Public hosted zones** | DNS resolution for the internet. |

**Routing policies – exam focus:**

| Policy | Description |
|--------|-------------|
| **Simple** | Single resource (e.g., one IP). |
| **Weighted** | Split traffic based on weights (e.g., 70% to one region, 30% to another). |
| **Latency** | Route users to the region with the lowest latency. |
| **Geolocation** | Route users based on their geographic location (e.g., US users to US servers). |
| **Failover** | Active‑passive – primary endpoint plus a secondary for failover. |
| **Multi‑value** | Return multiple IPs (health checks ensure only healthy ones are returned). |

## 10. Amazon RDS – Relational Database Service

**Amazon RDS** is a fully managed relational database service that supports multiple database engines.

### Supported Database Engines

- MySQL
- PostgreSQL
- MariaDB
- Oracle
- Microsoft SQL Server
- Amazon Aurora (MySQL/PostgreSQL‑compatible)

### Key Characteristics

| Characteristic | Description |
|----------------|-------------|
| **Managed service** | AWS handles patching, backups, replication, and failure recovery. |
| **Customer control** | You do **not** have root access or OS access to the RDS instance. |
| **VPC** | RDS is launched inside your VPC. |
| **Security** | Security Groups can be attached to RDS instances. |
| **Deployment** | Stand‑alone (single AZ) or **Multi‑AZ** (primary + standby in another AZ). |
| **Best practice** | Launch RDS in **private subnets** (no public/elastic IP). |
| **Backups** | Automated backups (with retention period) and manual snapshots. |

### Multi‑AZ RDS

- **Synchronous replication** – data is replicated to a standby instance in a different AZ.
- **Automatic failover** – if the primary fails, AWS automatically fails over to the standby.
- **High availability** – meets HA requirements (RTO of ~60 seconds).

### Read Replicas

- **Asynchronous replication** – read‑only copies of the primary database.
- Use for **read‑heavy workloads** (reporting, analytics, scaling read capacity).
- Can be promoted to a standalone primary if needed.

### OLTP vs. OLAP

| Aspect | OLTP (Online Transaction Processing) | OLAP (Online Analytical Processing) |
|--------|--------------------------------------|--------------------------------------|
| **Purpose** | Transactional operations (INSERT, UPDATE, DELETE). | Analytical queries (complex SELECT, aggregations). |
| **Example** | E‑commerce orders, banking transactions. | Data warehousing, business intelligence. |
| **AWS service** | RDS, Aurora, DynamoDB. | Redshift, Athena, EMR. |

## 11. Project 1 – Requirements 7, 8 & 9

**Requirement 7:** Launch an RDS in the VPC – ensure failover to another AZ in case of failure. Ensure database instances are secured at Layer 4.

**Design decisions:**
- Launch RDS in **private subnets** (no public access).
- Enable **Multi‑AZ** for automatic failover.
- **Security Group** on RDS: allow inbound traffic on the database port (e.g., 3306 for MySQL) only from the web/application Security Group.
- **NACL** on the private subnet: allow inbound/outbound database traffic only from/ to the web/application tier.

**Requirement 8:** Ensure that the data is encrypted as it is stored.

**Design decisions:**
- Enable **encryption at rest** using AWS KMS.
- Enable **encryption in transit** (SSL/TLS) for database connections.

**Requirement 9:** As traffic increases, the solution must have a component that decouples the web app tier from the database tier to avoid overwhelming the database.

**Design decisions:**
- Use **SQS** (Simple Queue Service) to decouple the web tier from the database tier.
- Web tier sends messages to SQS; database tier processes messages asynchronously.
- Use **RDS Read Replicas** to offload read queries from the primary database.

## 12. Key Architecture Pillars

### 12.1 Monolithic vs. Microservices Applications

| Aspect | Monolithic | Microservices |
|--------|------------|---------------|
| **Architecture** | Single, unified codebase. | Multiple independent services. |
| **Deployment** | Deployed as one unit. | Each service deployed independently. |
| **Scalability** | Scale the entire application. | Scale individual services. |
| **Development** | Single team, shared repository. | Multiple teams, multiple repositories. |
| **Fault isolation** | A failure in one component can affect the whole application. | Failures are isolated to individual services. |

### 12.2 High Availability and Fault Tolerance

| Term | Definition | AWS Example |
|------|------------|-------------|
| **High Availability** | Minimises downtime; the system is operational most of the time. | Multi‑AZ, Auto Scaling, ELB. |
| **Fault Tolerance** | System continues operating even when a component fails. | Redundancy across AZs, health checks, failover. |
| **RTO** | Maximum acceptable downtime. | Multi‑AZ RDS (failover in ~60 seconds). |
| **RPO** | Maximum acceptable data loss. | RDS automated backups (up to 5 minutes). |

### 12.3 Scalability

| Aspect | Description |
|--------|-------------|
| **Vertical Scaling** | Increase the size of an existing resource (e.g., `t2.micro` → `t3.large`). |
| **Horizontal Scaling** | Add more resources (e.g., add more EC2 instances). |
| **AWS service** | Auto Scaling Groups (horizontal scaling). |

### 12.4 Elasticity and Auto Scaling

| Aspect | Description |
|--------|-------------|
| **Elasticity** | Automatically scale resources up/down based on demand. |
| **AWS service** | **Auto Scaling Groups** – launch or terminate EC2 instances based on CloudWatch metrics (e.g., CPU utilisation > 70%). |

**Auto Scaling configuration:**
- **Launch template** – defines the EC2 instance configuration.
- **Scaling policy** – rules for scaling out/in (target tracking, scheduled, simple).
- **Health checks** – ELB health checks; Auto Scaling replaces unhealthy instances.

### 12.5 Elastic Load Balancing (ELB) 101

**ELB** automatically distributes incoming application traffic across multiple targets (EC2 instances, containers, IP addresses).

| Load Balancer Type | Layer | Use Case |
|--------------------|-------|----------|
| **Application Load Balancer (ALB)** | Layer 7 (HTTP/HTTPS) | Web applications, path‑based routing, host‑based routing. |
| **Network Load Balancer (NLB)** | Layer 4 (TCP/UDP) | High‑performance, low‑latency applications. |
| **Gateway Load Balancer (GWLB)** | Layer 3/4 | Third‑party virtual appliances (firewalls, IPS). |

**ALB features:**
- **Path‑based routing** – route `/api/*` to one target group, `/static/*` to another.
- **Host‑based routing** – route based on the hostname in the request.
- **Sticky sessions** – keep a user's session on the same instance.
- **Health checks** – detect unhealthy instances and stop sending traffic to them.

## 13. Project 1 – Requirements 10 & 11

**Requirement 10:** Ensure the web app tier is highly available across the two AZs. Load should be distributed evenly across the web instances.

**Design decisions:**
- Place EC2 instances (web tier) in both public subnets (AZ‑1a and AZ‑1b).
- Create an **Auto Scaling Group** across both AZs.
- Create an **Application Load Balancer (ALB)** in front of the web tier (distributes traffic evenly).
- Configure **health checks** so the ALB only sends traffic to healthy instances.

**Requirement 11:** The solution must be connected to the corporate datacenter with two connections: primary with low latency and a secure internet‑based backup.

**Design decisions:**
- **Primary connection:** **AWS Direct Connect** – private, dedicated connection (low latency, high bandwidth).
- **Backup connection:** **Site‑to‑Site VPN** over the internet (IPsec) – cost‑effective, quick to deploy, secure.

**Route 53 health checks and failover:** Use Route 53 health checks + failover routing to switch between connections if the primary fails.

## 14. Amazon CloudWatch 101 – Monitoring and Visibility

**Amazon CloudWatch** is a monitoring and observability service for AWS resources and applications.

### Core Components

| Component | Description |
|-----------|-------------|
| **Metrics** | Performance data (e.g., CPU utilisation, memory usage, disk I/O). |
| **Alarms** | Trigger actions based on metric thresholds (e.g., send notification, scale out). |
| **Logs** | Store, monitor, and access log files (e.g., application logs, system logs). |
| **Logs Insights** | Query and analyse logs using a SQL‑like language. |
| **Dashboards** | Visualise metrics and logs in custom dashboards. |
| **Events** | Respond to state changes (e.g., EC2 instance state changes). |

**Common metrics:**
- **EC2** – CPU utilisation, disk reads/writes, network in/out.
- **RDS** – CPU utilisation, database connections, read/write latency.
- **Lambda** – invocation count, duration, errors.

**CloudWatch Alarms:**
- **State:** OK, ALARM, INSUFFICIENT_DATA.
- **Actions:** Send SNS notification, Auto Scaling action (scale out/in), EC2 action (stop/terminate/reboot).

## 15. Amazon CloudTrail 101 – Auditing in AWS

**Amazon CloudTrail** provides a record of API calls made to AWS services.

| Aspect | Description |
|--------|-------------|
| **Purpose** | Audit, security analysis, operational troubleshooting. |
| **Scope** | Tracks all API calls (management plane and data plane events). |
| **Region** | By default, CloudTrail is enabled for each Region individually. |
| **Storage** | Logs are stored in S3 (and optionally CloudWatch Logs). |
| **Integrity** | Log file integrity validation to ensure logs have not been tampered with. |

### Types of Log Events

| Event Type | Description |
|------------|-------------|
| **Management Events** | Operations that change the state of AWS resources (e.g., `ec2:RunInstances`, `iam:CreateUser`). |
| **Data Events** | Operations on data within a service (e.g., `s3:GetObject`, `lambda:Invoke`). Data events are **not enabled by default**. |
| **Insight Events** | Identify unusual API activity (e.g., unusual call patterns). |

### Log File Integrity Validation

- CloudTrail logs are **encrypted** and can be validated to ensure they have not been altered.
- **Hash values** are calculated for each log file and stored in a digest file.
- **Digest files** are created every hour and can be used to verify the integrity of the logs.
