## 1. Virtualization 101

### What is Virtualization?

**Virtualization** is the technology that allows a single physical server (with 1 CPU, 1 RAM, 1 Hard Disk, 1 Network Card) to be divided into multiple virtual servers (e.g., 5 servers). Each virtual server runs its own operating system and appears as a standalone physical machine.

**How it works:** A **hypervisor** (also called a Virtual Machine Monitor) emulates hardware components – vCPU, vRAM, vHardDisk, vNetwork Card – for each virtual machine. The guest OS believes it has dedicated hardware, but it is actually sharing the physical resources.

**Hypervisor examples:** Xen (used by AWS), VMware ESXi, KVM, Hyper‑V.

**AWS and virtualization:** AWS EC2 uses **Xen virtualization** (and more recently Nitro Hypervisor). Each EC2 instance is a virtual machine running on a physical host.

### VMs vs. Containers

| Aspect | Virtual Machines (VMs) | Containers |
|--------|------------------------|------------|
| **Isolation** | Full OS isolation (kernel, filesystem, network). | Process‑level isolation (share host kernel). |
| **Resource overhead** | Heavy – each VM runs a full OS. | Lightweight – share host OS. |
| **Startup time** | Seconds to minutes. | Milliseconds. |
| **Portability** | Can run on any hypervisor. | Requires container runtime (Docker, Podman). |
| **Use case** | Legacy applications, strong isolation. | Microservices, modern applications. |

## 2. EC2 – Elastic Compute Cloud

**EC2 (Elastic Compute Cloud)** is AWS's flagship compute service – it provides resizable compute capacity in the cloud.

### Key Characteristics

| Characteristic | Description |
|----------------|-------------|
| **Root access** | You have full root access to each EC2 instance. |
| **Lifecycle** | Instances can be started, stopped, rebooted, or terminated. |
| **Tenancy** | Shared (with other customers) or dedicated host (physical server allocated to a single customer). |
| **Limits** | Default soft limit of 20 EC2 instances per account (can be increased). |
| **Placement** | Each EC2 instance is launched in a subnet within a specific Availability Zone (AZ). |
| **IP addressing** | Each instance has an IPv4 address; IPv6 is optional. |
| **Root volume** | The boot volume (root volume) can be EBS‑backed or Instance Store‑backed. |

### EC2 and EBS (Elastic Block Store)

| Aspect | EBS‑Backed EC2 | Instance Store‑Backed EC2 |
|--------|----------------|---------------------------|
| **Storage type** | Persistent block storage (network‑attached). | Ephemeral storage (physically attached to the host). |
| **Persistence** | Data persists after instance stop/termination (unless `DeleteOnTermination` is set). | Data is lost when instance is stopped or terminated. |
| **Speed** | Slower (network I/O). | Much faster (direct attach). |
| **Use case** | Most workloads – databases, application data. | Temporary data, cache, scratch space. |

**Root volume:** The boot volume of an EC2 instance. You can choose EBS or Instance Store for the root volume.

### Key Pair Authentication

- **SSH access:** You do not need a password to connect to a Linux EC2 instance.
- **Key pair:** You need a private key (`.pem` file) to connect via SSH. The public key is stored in AWS.
- **Download:** You can download the private key **only once** during instance launch. Keep it safe!

**Connecting to Linux EC2 instance:**

```bash
ssh -i /path/to/key.pem ec2-user@public-ip
```

## 3. EC2 Public, Private, and Elastic IPs

### IP Types

| IP Type | Description | Use Case |
|---------|-------------|----------|
| **Public IP** | Assigned automatically from AWS's pool. Changes when instance is stopped/started. | Direct internet access (web servers). |
| **Private IP** | Assigned from the VPC subnet. Fixed for the lifecycle of the instance. | Internal communication within the VPC. |
| **Elastic IP** | Static public IP that you own. Remains associated even if you stop/start the instance. | Public‑facing services that need a fixed IP (e.g., whitelisting). |

**Elastic IP use case – whitelisting:** If you need to whitelist your AWS infrastructure for third‑party services (e.g., API key validation, IP‑based access control), you assign an Elastic IP to your instance and whitelist that IP.

**Elastic IP limits:** Default limit of 5 Elastic IPs per account per Region (can be increased).

**NAT (Network Address Translation):**
- Allows private instances to access the internet without having public IPs.
- NAT Gateway (AWS managed) or NAT Instance (self‑managed) translates private IPs to a public IP.

## 4. Security Groups 101

A **Security Group** is a virtual firewall that controls inbound and outbound traffic at the instance (ENI) level.

### Key Characteristics

| Characteristic | Description |
|----------------|-------------|
| **Scope** | Applied at the instance's Elastic Network Interface (ENI) level. |
| **Rules** | You can only define **permit** rules (no explicit deny rules). |
| **Evaluation** | All rules are evaluated before a decision is made. |
| **Default limit** | Up to 16 security groups per instance interface (5 is default). |
| **Implicit deny** | There is an implicit deny rule at the end – if no rule matches, traffic is denied. |
| **Statefulness** | Security Groups are **stateful** – if you allow inbound traffic, the outbound response is automatically allowed (and vice versa). |
| **Changes** | Changes take effect immediately (no restart required). |

### Inbound vs. Outbound

| Direction | Controls |
|-----------|----------|
| **Inbound** | Traffic entering the instance (from clients, other services). |
| **Outbound** | Traffic leaving the instance (to external services, databases). |

### Possible Sources for Inbound Rules

- **IP address** (CIDR block or single IP)
- **Security Group** (allow traffic from instances in a specific security group)

**Client to Server Communication – Understanding Source/Destination Ports:**

When defining Security Group rules, you specify:
- **Source IP** (who is allowed)
- **Destination port** (which service on the instance is allowed)

**Example:** For a web server, allow inbound traffic from `0.0.0.0/0` (anywhere) to port `80` (HTTP) and port `443` (HTTPS). For SSH, restrict the source IP to your office IP range.

## 5. NACLs – Network Access Control Lists

**NACLs (Network Access Control Lists)** are virtual firewalls that control traffic at the **subnet level**.

### Key Characteristics

| Characteristic | Description |
|----------------|-------------|
| **Scope** | Applied at the subnet level (implied router). |
| **Rules** | You can define both **permit** and **deny** rules. |
| **Rule numbering** | Each rule has a sequence number. Rules are evaluated from lowest to highest sequence number. |
| **Implicit deny** | NACLs end with an explicit deny (`*` rule) – if no rule matches, traffic is denied. |
| **Statelessness** | NACLs are **stateless** – you must define both inbound and outbound rules for traffic to pass. |
| **Default behavior** | Each subnet has a default NACL (allows all inbound and outbound). |

### NACL vs. Security Group – Key Differences

| Feature | Security Group | NACL |
|---------|----------------|------|
| **Scope** | Instance level (ENI). | Subnet level. |
| **Rules** | Only allow rules. | Allow and deny rules. |
| **State** | Stateful – return traffic automatically allowed. | Stateless – return traffic must be explicitly allowed. |
| **Order** | All rules evaluated. | Rules evaluated in sequence number order. |
| **Implicit rule** | Implicit deny at the end. | Explicit deny (`*`). |
| **Changes** | Apply immediately. | Apply immediately. |

### Whitelisting vs. Blacklisting

| Approach | Description | Use with |
|----------|-------------|----------|
| **Whitelisting** | Allow only specific traffic, deny everything else. | Security Groups (allow rules only). |
| **Blacklisting** | Deny specific traffic, allow everything else. | NACLs (allow + deny rules). |

**Why whitelisting is better for security:** It is more secure to explicitly allow only what is needed and deny everything else by default.

## 7. Project 1 – Requirements 2 & 3

**Design a solution for a multi‑tier web application hosted in AWS.**

**Requirement 1 (completed in Part 1):**
- VPC with CIDR `10.0.0.0/16`
- 2 public subnets (`10.0.10.0/24`, `10.0.20.0/24`) in two AZs
- 2 private subnets (`10.0.100.0/24`, `10.0.200.0/24`) in the same AZs

**Requirement 2:** Launch two EBS‑backed EC2 instances, one in each AZ, serving as web and application tiers. They should be accessible from the internet.

**Design decisions:**
- Place the EC2 instances in the **public subnets** (to be accessible from the internet).
- Attach a **Security Group** that allows:
  - Inbound: HTTP (80), HTTPS (443) from anywhere (`0.0.0.0/0`)
  - Inbound: SSH (22) from your office IP (or a bastion host)
- Use **Elastic IPs** if you need a fixed public IP for whitelisting.

**Requirement 3:** Design VPC security to ensure access control at **Layer 4** (Transport Layer – TCP/UDP) at both the subnet and compute levels.

**Security controls:**
- **Subnet level:** Use **NACLs** on both public and private subnets:
  - Allow only necessary inbound/outbound traffic (e.g., public subnet: allow HTTP/HTTPS from internet, allow SSH from office).
  - Private subnet: restrict inbound traffic to only from the application/security groups.
- **Compute level:** Use **Security Groups**:
  - Web/App instances: allow HTTP/HTTPS from anywhere, SSH from office.
  - Database instances (later): allow only from the web/app security group on the database port (e.g., 3306 for MySQL).

## 8. Encryption 101

**Always encrypt sensitive data:**
- **In transit** – data moving across the network.
- **At rest** – data stored on disk.

### Encryption in Transit – Asymmetric Keys (Session Negotiation)

Asymmetric encryption uses **key pairs**: a public key (shared) and a private key (secret). Data encrypted with the public key can only be decrypted with the private key.

**Example: SSL/TLS handshake (HTTPS):**
1. Client requests secure connection.
2. Server sends its public key (certificate).
3. Client encrypts a session key with the server's public key.
4. Server decrypts with its private key.
5. Both sides now share a symmetric session key for the rest of the session.

### Encryption in Transit – Symmetric Keys

Symmetric encryption uses **one shared key** for both encryption and decryption. It is faster and more efficient than asymmetric encryption.

**Combined approach:** Asymmetric encryption (public/private key) is used to securely exchange the symmetric key. Once exchanged, symmetric encryption is used for the data transfer.

**AWS recommendation:** Use **symmetric encryption** where possible because it is faster and more efficient. Asymmetric is used primarily for key exchange and digital signatures.

### Encryption at Rest

- Data stored on EBS volumes, S3 buckets, RDS databases, etc.
- AWS services support encryption using **AWS KMS** (Key Management Service).

## 9. AWS KMS 101 – Key Management Service

**AWS KMS (Key Management Service)** is a managed service that allows you to create and manage cryptographic keys for encrypting your data.

### Key Characteristics

| Characteristic | Description |
|----------------|-------------|
| **Managed service** | AWS manages the infrastructure; you manage the keys. |
| **FIPS‑140‑2 compliant** | Meets US government security standards. |
| **Integration** | Integrates with many AWS services (EBS, S3, RDS, etc.). |
| **High availability** | Highly durable and available. |
| **Auditing** | Integrates with CloudTrail for audit and compliance. |
| **Pricing** | $1/month per customer‑managed key. AWS‑managed keys are free. |
| **Regional service** | KMS keys are Regional (cannot be used across Regions). |
| **Key rotation** | AWS manages automatic key rotation (yearly). You can also configure custom rotation. |

### Customer Master Keys (CMKs)

- **AWS‑managed CMKs:** Created automatically by AWS services (free). Example: `aws/s3`, `aws/ebs`.
- **Customer‑managed CMKs:** Created by you (cost $1/month). You have full control over key policies, rotation, and usage.

### Encryption Limits

- CMKs can encrypt/decrypt data **up to 4 KB**.
- For larger data (e.g., EBS volumes, S3 objects), your application or service uses **data keys** (envelope encryption). KMS generates and manages the encryption keys but does **not** store the customer data.

**Envelope encryption:** KMS generates a data key (encrypted). The data key is used to encrypt the actual data. The encrypted data key is stored alongside the data.

## 10. S3 – Simple Storage Service 101

**S3 (Simple Storage Service)** is AWS's object storage service. It is highly scalable, durable, and accessible from anywhere.

### Block Storage vs. Object Storage

| Aspect | Block Storage (EBS) | Object Storage (S3) |
|--------|---------------------|---------------------|
| **Data structure** | Fixed‑sized blocks (volumes). | Objects (files) with metadata. |
| **Access** | Attached to a single EC2 instance (like a hard drive). | Accessed via HTTP/HTTPS (REST API). |
| **Persistence** | Persistent if EBS‑backed. | Very high durability (11 nines). |
| **Use case** | Operating systems, databases. | Static files, backups, data lakes. |

### S3 Key Characteristics

| Characteristic | Description |
|----------------|-------------|
| **Data limit** | Unlimited total capacity. Individual object size: up to 5 TB. |
| **Region‑based** | S3 buckets are created in a specific Region. |
| **Internet accessible** | S3 is accessible from the internet (public or private via VPC endpoints). |
| **Bucket name** | Globally unique across all AWS accounts and Regions. |
| **Folder concept** | There are no real folders in S3 – prefixes are used to mimic folders (e.g., `folder1/file.txt`). |
| **Ownership** | The account that created the bucket is the owner. |
| **Durability** | 99.999999999% (11 nines) durability for Standard storage class. |

**Access control:**
- **Bucket policies** – IAM‑like JSON policies that control access to the bucket and its objects.
- **ACLs** – legacy access control mechanism (not recommended; use bucket policies).
- **Presigned URLs** – provide temporary access to specific objects.

## 11. Quick Reference Table

| Topic | Summary |
|-------|---------|
| **Virtualization** | Hypervisor emulates hardware for multiple VMs. AWS uses Xen/Nitro. |
| **EC2** | Resizable compute capacity, launched in a subnet, uses key pairs for SSH. |

| **Instance Store** | Ephemeral storage, physically attached, faster but non‑persistent. |

   - Enable static website hosting (if public).

   - Create a customer‑managed KMS key.
   - Encrypt an EBS volume using that key.
