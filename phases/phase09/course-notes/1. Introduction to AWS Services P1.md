## 2. Introduction to Cloud Computing

### 2.1 On‑Premises Data Centers vs. Cloud

| Aspect | On‑Premises | Cloud |
|--------|-------------|-------|
| **Cost model** | CAPEX – large upfront investment. | OPEX – pay‑as‑you‑go. |
| **Hardware** | You buy, maintain, and replace servers. | Provider owns hardware; you consume services. |
| **Staff** | You hire sysadmins, network engineers, facility managers. | Provider manages infrastructure staff. |
| **Space** | You pay for real estate, power, cooling. | No real estate costs. |
| **Security** | You control physical and network security. | Shared responsibility – provider secures infrastructure, you secure your data. |
| **Scalability** | Limited by physical capacity. | On‑demand, virtually unlimited. |
| **Time to market** | Weeks to months (procurement, shipping, racking). | Minutes to hours (self‑service). |

**Why cloud won:** The cloud is like **electricity or water** – you consume what you need and pay only for what you use.

**Before cloud:** Companies used **hosting** (dedicated servers or VPS) – better than on‑premises but still required managing the OS and applications.

### 2.2 Cloud Types: Private, Public, Hybrid, Multi‑Cloud

| Model | Description | When to Use |
|-------|-------------|-------------|
| **Private Cloud** | Dedicated infrastructure for a single organisation. Can be on‑premises or hosted by a third party. | Sensitive data, strict compliance, legacy systems. |
| **Public Cloud** | Shared infrastructure across multiple tenants (AWS, Azure, GCP). | Most workloads – web apps, mobile backends, dev/test. |
| **Hybrid Cloud** | Combination of public and private clouds. Resources are shared between them. | Gradual migration, bursting (public for spikes), disaster recovery. |
| **Multi‑Cloud** | Using multiple public cloud providers simultaneously. | Avoid vendor lock‑in, best‑of‑breed services, disaster recovery. |

**Hybrid Multi‑Cloud:** A combination of hybrid cloud (public + private) with multiple public cloud providers. Most complex but offers maximum flexibility.

### 2.3 Cloud Service Models: IaaS, PaaS, SaaS, XaaS

| Model | What You Manage | What Provider Manages | AWS Example |
|-------|-----------------|-----------------------|-------------|
| **IaaS** | OS, applications, data, networking. | Hardware, virtualization, storage infrastructure. | EC2 |
| **PaaS** | Application code, data. | OS, runtime, middleware, infrastructure. | Elastic Beanstalk, Lambda |
| **SaaS** | User data, configuration. | Everything else – application, infrastructure, updates. | Office 365, WorkSpaces |
| **XaaS** | "Anything as a Service" – catch‑all for other services (DBaaS, FaaS, etc.). | Varies. | RDS (DBaaS), Lambda (FaaS) |

**The core concept:** The **Shared Responsibility Model** defines who manages what – on‑premises, the customer manages everything. In the cloud, the provider takes on more responsibility as you move up the stack (IaaS → PaaS → SaaS).

### 2.4 Top Cloud Players – Gartner Magic Quadrant

Gartner evaluates cloud providers based on **Completeness of Vision** (future strategy) and **Ability to Execute** (operational excellence, market share).

**Leaders (2026):**
- **AWS** – Most mature, broadest service portfolio.
- **Microsoft Azure** – Strong enterprise integration (Microsoft ecosystem).
- **Google Cloud Platform (GCP)** – Leaders in AI/ML and data analytics.

## 3. Introduction to AWS Services (High‑Level)

### 3.1 AWS Global Infrastructure

- **Regions:** 37 (as of 2025) – geographical areas containing multiple Availability Zones.
- **Availability Zones (AZs):** 107+ – one or more data centres with independent power, cooling, and networking.
- **Edge Locations:** 550+ – used by CloudFront for caching content closer to users.
- **Direct Connect Locations:** 120+ – private connections to AWS.

### 3.2 AWS Regions and Availability Zones

| Concept | Definition |
|---------|------------|
| **Region** | A geographical area with multiple AZs (e.g., `us-east-1` – N. Virginia). |
| **Availability Zone** | One or more data centres within a Region (e.g., `us-east-1a`, `us-east-1b`). |
| **Edge Location** | Used by CloudFront to cache content globally. |

### 3.3 Walkthrough the AWS Website

- **AWS Management Console** – web UI for managing services.
- **AWS Documentation** – [docs.aws.amazon.com](https://docs.aws.amazon.com) – official guides, API references.
- **AWS Free Tier** – limited free usage for 12 months (EC2, S3, RDS, etc.).

### 3.4 IAM 101 – Identity and Access Management

**IAM** is like a **security guard** – it controls **who** you are (authentication) and **what** you're allowed to do (authorization).

**IAM features:**
- **Shared access** to AWS accounts (multiple users).
- **Permissions** follow the user across all Regions.
- **Supported identities:** Users, Groups, Roles, Federated Users.

**Principle of least privilege:** Grant only the permissions required to perform a task.

### 3.5 VPC 101 – Virtual Private Cloud

**VPC** is your **virtual data center** in AWS – a logically isolated section of the AWS cloud where you can launch resources.

**VPC components:**
- CIDR block and subnets
- Implied router
- Route tables
- Internet Gateway (IGW)
- Virtual Private Gateway (VPG)
- Security Groups
- Network Access Control Lists (NACLs)

### 3.6 Public and Private Subnets

| Subnet Type | Definition |
|-------------|------------|
| **Public Subnet** | A subnet with an **Internet Gateway** attached. Its route table has a default entry pointing to the IGW. |
| **Private Subnet** | A subnet **without** a route to the Internet Gateway. Cannot be accessed directly from the internet. |

### 3.7 Hybrid Connectivity Options

| Option | Description | Pros | Cons |
|--------|-------------|------|------|
| **VPN** | Site‑to‑site VPN over the internet (IPsec). | Quick to deploy, cost‑effective, secure. | Not reliable (public internet), variable performance. |
| **Direct Connect** | Private, dedicated connection to AWS. | Reliable, low latency, high bandwidth. | Long lead time, expensive. |

**Security:** Direct Connect can be combined with IPsec for additional security (encrypted private connection).

## 4. IAM Deep Dive

### 4.1 IAM Features

| Feature | Description |
|---------|-------------|
| **Shared access** | Grant permissions to multiple users without sharing credentials. |
| **Granular permissions** | Define permissions for specific resources (e.g., only S3 bucket `my-bucket`). |
| **Multi‑factor authentication (MFA)** | Require MFA for sensitive operations. |
| **Identity federation** | Integrate with corporate Active Directory or third‑party identity providers. |
| **Auditing** | Track API activity via CloudTrail. |
| **Access keys** | Programmatic access (CLI, SDK, API). |

### 4.2 IAM Identities

| Identity | Description |
|----------|-------------|
| **Users** | Individual users with their own credentials (password + access keys). |
| **Groups** | Collections of users. Attach policies to groups to manage permissions centrally. |
| **Roles** | Assumed by users, services, or applications to gain temporary permissions. |
| **Federated Users** | Users from external identity providers (Active Directory, Google, etc.). |

### 4.3 IAM Best Practices

| # | Best Practice |
|---|---------------|
| 1 | **Lock away root user** – do not use the root user for daily operations. |
| 2 | **Create IAM users** for every person/service. |
| 3 | **Use AWS managed policies** when possible (pre‑defined by AWS). |
| 4 | **Use groups** to manage permissions centrally. |
| 5 | **Least privilege** – grant only the permissions needed. |
| 6 | **Strong password policy** – enforce complexity and rotation. |
| 7 | **Enable MFA** for privileged users (root and admin). |
| 8 | **Use roles for EC2 instances** – never store credentials on instances. |
| 9 | **Delegate by using roles** – never share credentials. |
| 10 | **Rotate credentials** regularly (access keys, passwords). |
| 11 | **Remove unnecessary credentials** – delete unused users/keys. |
| 12 | **Use policy conditions** for extra security (e.g., IP restrictions, MFA requirement). |
| 13 | **Monitor activities** with CloudTrail, AWS Config, and GuardDuty. |
| 14 | **Use access levels** – understand the access level of each permission (List, Read, Write, Tagging, Permissions management). |

### 4.4 Access Types

| Access Type | Credentials | Use Case |
|-------------|-------------|----------|
| **Console access** | Username + password | Web UI (Management Console). |
| **Programmatic access** | Access Key ID + Secret Access Key | CLI, SDK, API calls. |

## 5. VPC Deep Dive

### 5.1 VPC Components

| Component | Description |
|-----------|-------------|
| **CIDR block** | The IP address range for your VPC (e.g., `10.0.0.0/16`). |
| **Subnets** | Logical subdivisions of the VPC within an Availability Zone. |
| **Implied router** | A built‑in router that routes traffic between subnets. |
| **Route tables** | Define rules for routing traffic (e.g., local routes, internet routes). |
| **Internet Gateway (IGW)** | Allows communication between the VPC and the internet. |
| **Virtual Private Gateway (VPG)** | Connects the VPC to on‑premises networks (VPN or Direct Connect). |
| **Security Groups** | Stateful, instance‑level firewalls. |
| **Network Access Control Lists (NACLs)** | Stateless, subnet‑level firewalls. |

### 5.2 Internet Gateway vs. Virtual Private Gateway

| Gateway | Purpose | Attached To |
|---------|---------|-------------|
| **Internet Gateway** | Allows internet traffic into/out of the VPC. | VPC (one per VPC). |
| **Virtual Private Gateway** | Connects VPC to on‑premises via VPN or Direct Connect. | VPC (one per VPC). |

### 5.3 Public vs. Private Subnets

**Public subnet:**
- Has a **route to the Internet Gateway** in its route table.
- Instances in a public subnet must have **public IP addresses** to be reachable from the internet.

**Private subnet:**
- **No route to the Internet Gateway**.
- Instances cannot be reached from the internet (unless via NAT Gateway, VPN, or Direct Connect).

**NAT Gateway:** Allows private subnet instances to access the internet (for updates, patches, etc.) while remaining unreachable from the internet.

### 5.4 Hybrid Connectivity Options

| Option | Description |
|--------|-------------|
| **VPN** | Site‑to‑site IPsec VPN over the internet. Quick to deploy, cost‑effective. |
| **Direct Connect** | Private, dedicated physical connection. Low latency, high bandwidth, but longer lead time. |

**Combined approach:** Use **Direct Connect + IPsec** for encrypted private connectivity.

## 6. Project 1 – Requirement 1

**Design a solution for a web application that will be hosted in AWS to satisfy the following requirements:**

1. The app will be launched in a VPC with CIDR block `10.0.0.0/16` with:
   - **2 public subnets** in two different Availability Zones (use `10.0.10.0/24` and `10.0.20.0/24`).
   - **2 private subnets** in the same AZs as above (use `10.0.100.0/24` and `10.0.200.0/24`).

**Architecture diagram (conceptual):**

```

│                          VPC (10.0.0.0/16)                            │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐ │
│  │                        AZ-1a                                      │ │
│  │  ┌─────────────────────────────┐  ┌─────────────────────────────┐│ │
│  │  │  Public Subnet 1             │  │  Private Subnet 1           ││ │
│  │  │  (10.0.10.0/24)             │  │  (10.0.100.0/24)            ││ │
│  │  └─────────────────────────────┘  └─────────────────────────────┘│ │
│  └───────────────────────────────────────────────────────────────────┘ │
│                                                                         │
│  ┌───────────────────────────────────────────────────────────────────┐ │
│  │                        AZ-1b                                      │ │
│  │  ┌─────────────────────────────┐  ┌─────────────────────────────┐│ │
│  │  │  Public Subnet 2             │  │  Private Subnet 2           ││ │
│  │  │  (10.0.20.0/24)             │  │  (10.0.200.0/24)            ││ │
```

**Discussion questions:**
- Which resources should go in the public subnets? (ALB, Bastion, NAT Gateway)
- Which resources should go in the private subnets? (EC2 instances, RDS, application servers)
- Why use 2 AZs? (Fault tolerance, high availability)

## 8. Practice Lab – Verify Your Understanding

1. **Create an IAM user (hands‑on):**
   - Create a new IAM user with **console access** (password) and **programmatic access** (access keys).
   - Assign the `AdministratorAccess` policy to a group and add the user to the group.

2. **Enable MFA on your root account:**
   - Use Google Authenticator or a similar app.
   - Set up MFA for your root user.

3. **Create a VPC (hands‑on):**
   - Go to VPC → Your VPCs → Create VPC.
   - Use the CIDR block `10.0.0.0/16`.
   - Create 2 public subnets (`10.0.10.0/24` and `10.0.20.0/24`) in different AZs.
   - Create 2 private subnets (`10.0.100.0/24` and `10.0.200.0/24`) in the same AZs.

4. **Attach an Internet Gateway:**
   - Create an Internet Gateway and attach it to your VPC.
   - Update the route tables for public subnets to route `0.0.0.0/0` to the IGW.

5. **Cost budgets:**
   - Set up a budget of $10/month with an alert at 80%.
